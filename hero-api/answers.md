## Part 1 — SQL Warm-up

### Question 1

1. `INSERT INTO team (name, headquarters) VALUES ('Avengers', 'Los Angeles');`

   **UNIQUE** constraint blocks it because a team named `Avengers` already exists, and `team.name` must be unique.

2. `INSERT INTO hero (name, team_id) VALUES ('Ghost', 99);`

   **FOREIGN KEY** constraint blocks it because `team_id = 99` does not reference an existing row in the `team` table.

3. `INSERT INTO hero (age) VALUES (30);`

   **NOT NULL** constraint blocks it because the required `name` column is not provided.

4. `DELETE FROM team WHERE id = 1;`

   **FOREIGN KEY** constraint blocks it because heroes still reference team `id = 1`. Deleting the team would leave invalid foreign-key references.

### Question 2

The foreign key is on `hero` because one team can have many heroes, while each hero belongs to at most one team.

Therefore, the `hero` table stores `team_id` to identify which team each hero belongs to. Putting the foreign key on `team` would not efficiently represent multiple heroes belonging to the same team.

### Question 3

A many-to-many relationship between heroes and missions requires three tables:

```text
hero
----

...

mission
-------
id (PK)
title
...

heromissionlink
---------------
hero_id (PK, FK → hero.id)
mission_id (PK, FK → mission.id)
```

The link table represents the many-to-many relationship:

This allows one hero to participate in many missions and one mission to contain many heroes.

The database generates the primary key when the row is inserted. Before insertion, the Python object's `id` can therefore be `None`; after the database generates it and the object is refreshed, it becomes an integer.

## Part 4 — Engine, Tables and Session

### Question 7

The SQLAlchemy-generated `CREATE TABLE hero` is similar to the manually written SQL, but there are several differences.

The manually written table used types such as:

```sql
VARCHAR
INTEGER
```

SQLModel/SQLAlchemy generates PostgreSQL-compatible types based on the Python type annotations.

SQLModel also creates indexes for fields declared with `index=True`, such as `hero.name`. The `team_id` column has a foreign-key constraint referencing `team(id)`, and the primary key is generated by the database.

The important constraints are still represented:

- `id` → primary key
- `name` → NOT NULL and indexed
- `secret_name` → NOT NULL
- `team_id` → nullable foreign key to `team.id`

### Question 8

No, `CREATE TABLE` is not executed again for an existing table when the application is restarted.

`create_all()` checks whether the tables already exist. If they exist, it does not recreate or modify them.

Therefore, `create_all()` is useful for creating missing tables, but it does not perform schema migrations such as adding, removing, or renaming columns.

## Part 5 — CRUD Endpoints for Heroes

### Question 10

If `session.commit()` is commented out, `session.add()` only places the object in the session. It does not permanently save the row to the database.

Without `commit()`, the transaction is not committed, so the new hero is not persisted. A subsequent database query will not contain the new row.

`session.add()` makes the object pending in the current SQLAlchemy session. `session.commit()` actually commits the transaction and persists the INSERT.

`session.refresh()` is needed to reload the object from the database after the commit. This is especially important for values generated by the database, such as the new primary key.

## Part 6 — Teams, Filtering, Pagination and Errors

### Question 13

For:

```text
GET /heroes?min_age=18&team_id=1
```

the SQL printed by `echo=True` uses bound parameters, conceptually:

```sql
SELECT ...
FROM hero
WHERE hero.age >= %(age)s
  AND hero.team_id = %(team_id)s
ORDER BY hero.id
LIMIT ...
OFFSET ...
```

The actual values `18` and `1` are passed separately as parameters rather than being directly concatenated into the SQL string.

This is safe against SQL injection because SQLAlchemy uses parameterized queries and treats the supplied values as data rather than executable SQL code.

---

### Question 14

Filtering in the database is better because the database can filter, sort, and paginate the data before sending the results to the application.

For example:

```python
select(Hero).where(Hero.age >= 18)
```

allows PostgreSQL to perform the filtering.

Filtering after loading all rows into Python would transfer unnecessary data from the database, consume more memory, and become inefficient as the table grows.

## Part 9 — Migrations with Alembic

### Question 17

No, there was initially no `power` column in the PostgreSQL `hero` table.

Adding:

```python
power: str | None = None
```

to the SQLModel definition changes the Python model but does not automatically modify an existing database table.

When `GET /heroes` was called before the migration, the application returned an Internal Server Error because SQLAlchemy generated a query that expected `hero.power`, but the actual PostgreSQL table did not yet contain that column.

Dropping all tables and running `create_all()` again is not acceptable in production because it would delete existing production data. Database schema changes should instead be applied through migrations that preserve existing data.

---

### Question 18

The generated `upgrade()` function was:

```python
def upgrade() -> None:
    op.add_column(
        'hero',
        sa.Column(
            'power',
            sqlmodel.sql.sqltypes.AutoString(),
            nullable=True
        )
    )
```

It adds a nullable `power` column to the `hero` table.

The generated `downgrade()` function was:

```python
def downgrade() -> None:
    op.drop_column('hero', 'power')
```

It removes the `power` column from the `hero` table.

Therefore:

- `upgrade()` applies the schema change.
- `downgrade()` reverses the schema change.

---

### Question 19

Alembic stores the current database revision in the `alembic_version` table.

In this project, the table contained:

```text
version_num
------------
9a4871c40aff
```

The `migrations/` folder should be committed to Git because it contains the versioned migration scripts. These scripts allow other developers, CI/CD systems, and production environments to reproduce the database schema changes and upgrade or downgrade the database consistently.

The database's current revision alone is not enough; the migration scripts are needed to describe how to move between schema versions.

---

### Question 20

After renaming `secret_name` to `alias` in the model, Alembic generated:

```python
op.add_column(
    'hero',
    sa.Column(
        'alias',
        sqlmodel.sql.sqltypes.AutoString(),
        nullable=False
    )
)

op.drop_column('hero', 'secret_name')
```

Alembic interpreted the change as adding a new column and removing the old column rather than as a column rename.

This is dangerous because dropping `secret_name` would permanently remove the existing values stored in that column. Also, the new `alias` column was generated as `NOT NULL`, which can cause problems when adding it to an existing table containing rows.

For a simple column rename, the migration should use a rename operation, for example:

```python
op.alter_column(
    'hero',
    'secret_name',
    new_column_name='alias'
)
```

This changes the column name while preserving the existing data.

The downgrade should rename `alias` back to `secret_name`.

The generated migration was not applied. It was deleted afterward, and the model was restored to use `secret_name`.
